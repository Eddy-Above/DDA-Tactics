| 2026-08-19 | Pages & Components, Dependency Graph, Blast Radius, Cross-Cutting Concerns | **Fix: a Jumper couldn't finish a Charge `[Pass]` in the air (and couldn't jump into air at all).** Aiming a Charge `[Pass]` upward into open air always painted the landing marker red and silently swallowed the confirming click, so the attack could never be thrown. The cause was not in the charge code — the charge flow reuses the shared movement pipeline and never restricts *how* the attacker moves. It was the shared landing rule: `canLandOn()` in `utils/movementRules.ts` treated an air cell as landable **only if `caps.canFly`**, so a jumper was never allowed to end in air. Because `composables/useMapMovement.ts`'s `computeReachable()` filters candidate cells through the same predicate, this also meant **ordinary jump movement could never cross a gap or rise into open air** — the `Jumper`/`Advanced Mobility: Jumper` qualities effectively only bought vertical *step-up*, not jumping. `canLandOn()` now takes an optional trailing `origin?: Vec3` and a private `canJumpTo()` helper; both air branches accept `caps.canFly || canJumpTo(pos, origin, caps)`, capping the climb at `caps.jumpHeight` (level and descending jumps pass trivially, the latter simply resolving as a fall). Omitting `origin` keeps the old fliers-only semantics, so the change is additive for every other caller. A second, quieter bug would have defeated the fix on its own: `MapCanvas.vue`'s local `getAttackerCapabilities()` called `detectCapabilities(quals, 0, 0, 0)`, hard-zeroing `jumpRange`/`jumpHeight` (its comment claimed landing checks didn't use them), and it *couldn't* be fixed in place because `MapCanvas`'s `digimonMap` prop is the trimmed canvas map with no `baseStats`. It was deleted; capabilities now arrive as a new **`attackerCaps` prop** built in `EncounterMap.vue` by reusing the existing `npcMoveCaps()` (real stance-adjusted movement + stage bonus), so the `[Pass]` landing rule and the movement-range rule cannot drift apart. Server side, a jumper left hovering at end of turn is handled by the **existing** gravity path: `combatSpatial.ts`'s `getFallerProfile()` now **derives** `airborneByJump` (`explicit flag || has the extra-movement/jumper quality`) instead of reading a flag nothing ever set, so `resolveFall` short-circuits its damage to **0** and `endOfTurnGravity` drops the unit for free. Deriving is sound because every displacement path (`pushPull`, clash throw, intercede throw) already calls `resolveFall` at the moment of displacement, so anything *still* airborne when gravity runs got there under its own movement. Persisting the flag instead would have meant threading a participant write through the WebSocket move path, which carries positions only. Verified: non-jumpers and fliers are unaffected, and the jump-height cap is enforced rather than bypassed. |

## 4. Data Models & Storage
> Last verified: 2026-04-14

**Sources:** `server/db/schema.ts`, `server/db/index.ts`, `drizzle.config.ts`

**Engine:** PostgreSQL. **ORM:** Drizzle. **Migrations:** `server/db/migrations/` (0000–0019; note: 0002 is missing — sequence gap, appears intentional). No caching layer (no Redis). No message queue.

> **Migration tooling note (2026-07-08):** `server/db/migrations/meta/` snapshots/journal (`drizzle-kit generate`'s bookkeeping) haven't been updated since `0006_add_granted_inspiration` — migrations `0007`–`0014` exist as `.sql` files but aren't registered in `_journal.json`. `npm run db:generate` will misbehave (diffs against the stale 0006 snapshot) until this is reconciled; the actual sync mechanism in practice is `npm run db:push` (schema.ts ↔ live DB introspection, journal-independent). `0014_add_roll_log.sql` was hand-written to match the existing plain-SQL migration style rather than generated, for this reason.
>
> **Applying a new migration (verified 2026-07-29):** `_journal.json` still ends at `0006`, so **`npm run db:migrate` silently skips `0007`–`0018`** — an unregistered `.sql` file is never executed. `run-migrations.mjs` doesn't help either; it only executes `init-db.sql`, not the migrations directory. In practice a new migration is applied either by `npm run db:push` (introspects `schema.ts` against the live DB and generates the diff — journal-independent, but review its plan, it acts on whatever drift it finds) or by running the `.sql` by hand against `DATABASE_URL` (the pattern `migration-fix.sql` in the repo root came from). Hand-written migrations here use `ADD COLUMN IF NOT EXISTS` so a repeat run is a no-op.

All 34 `jsonb` columns listed below are native Postgres `jsonb` (migration 0013 converted them from `text`); server routes pass/receive parsed objects/arrays directly with no manual `JSON.parse`/`JSON.stringify`. `server/utils/parsers.ts` (formerly `parseTamerData`/`parseDigimonData`/`safeJSONParse`/`ensureArray`) was removed as part of this conversion.

## 8. Cross-Cutting Concerns
> Last verified: 2026-04-14

**Sources:** `middleware/campaign-access.ts`, `middleware/dm-access.ts`, `middleware/settings-access.ts`, `server/utils/password.ts`, `server/utils/session.ts`, `server/utils/campaignAuth.ts`, `server/utils/ownership.ts`, `server/api/auth/*`, `server/api/campaigns/[id]/verify-password.post.ts`, `server/api/campaigns/[id]/my-access.get.ts`, `server/api/campaigns/[id]/grants/*`, `server/api/campaigns/[id]/tamer-grants/*`, `server/api/campaigns/[id]/tamers/[tamerId]/public-access.put.ts`, `nuxt.config.ts`

### Auth Flow

Two independent, coexisting systems as of 2026-07-12 — passwords are the original mechanism and remain fully functional; accounts are optional and layer on top.

**1. Campaign passwords (original, unchanged in spirit):**
- Cookie-based boolean flags, no server-side validation on their own: `campaign-access-{campaignId}` (player) / `campaign-dm-{campaignId}` (DM), each set client-side via Nuxt's `useCookie()` (readable by JS, value literally `'true'`, 30-day TTL) after `POST /api/campaigns/[id]/verify-(dm-)?password` succeeds.
- Password storage: PBKDF2-SHA512 (`salt:hash` hex, `server/utils/password.ts`) in `campaigns.passwordHash`/`dmPasswordHash` — **not bcrypt**, despite this doc previously saying so.
- For a campaign with **no owner** (`campaigns.ownerId IS NULL` — every pre-2026-07-12 campaign, plus any created while logged out), this is the *entire* access model, completely unchanged: DM password holders get full access including Settings and Delete.

**2. Optional accounts (2026-07-12, new):** Username + password only, no email/personal data, self-serve registration.
- **Real server-side sessions** — the first server-validated identity concept in this app. `users`/`sessions`/`campaignAccessGrants` tables (see Data Models). Session cookie (`session`) is `httpOnly`/`sameSite: lax`/`secure`-in-prod, set server-side via h3's `setCookie` in `server/utils/session.ts` (`createSession`/`getSessionUser`/`destroySession`) — deliberately **not** the client `useCookie()` pattern used for the password flags above, since this is a real credential-backed session.
- **Campaign ownership:** `campaigns.ownerId` is stamped only at creation time (`POST /api/campaigns`) if the creator was logged in, and is **never reassigned afterward** — no claim/transfer flow exists or is planned. Owned campaigns unlock **grants**, now split across two tables (redesigned 2026-08-20, migration 0020): an owner can give a specific account a `dmRole` (`'co-dm'` = all GM tools, `'co-owner'` = full owner-equivalent power incl. Settings/Delete/grant management) via `campaignAccessGrants` (one row per campaign+account), and independently grant any number of accounts access to any number of individual tamers via `tamerAccessGrants` (one row per tamer+account, true many-to-many). A tamer is also reachable by anyone (no grant needed) if its `publicAccess` flag is true — see the `tamers` table in Data Models; this **replaced** the old `playerScope: 'all' | 'specific'` model outright (the broad "all tamers" scope was dropped, not kept alongside the new per-tamer grants; pre-existing `'specific'` grants were backfilled into `tamerAccessGrants`). `server/utils/campaignAuth.ts`'s `getMyCampaignAccess(event, campaignId)` is the single source of truth for "what can the current session do here" (`{isOwner, isCoOwner, isCoDm, accessibleTamerIds}`), exposed client-side via `GET /api/campaigns/[id]/my-access`.
- **Middleware (three-tier, all account-checks are additive to the existing password checks, tried first):**
  - `middleware/campaign-access.ts` — base "can view this campaign" gate. Password cookie OR *any* grant (`isOwner`/`isCoOwner`/`isCoDm`/`accessibleTamerIds.length > 0`) passes.
  - `middleware/dm-access.ts` — GM tool pages (library create/edit, maps). DM password cookie OR `isOwner`/`isCoOwner`/`isCoDm`.
  - `middleware/settings-access.ts` (**new**, replaces `dm-access.ts` specifically on `settings.vue`) — for ownerless campaigns, defers entirely to the legacy DM-password check (unaffected). For owned campaigns, requires `isOwner`/`isCoOwner`; **the DM password alone no longer reaches Settings** once a campaign has an owner (it still grants every other GM tool via `dm-access.ts`).
  - **Fix (2026-07-12):** all three now call `useRequestFetch()` (not bare `$fetch`) for their internal `GET .../my-access` check — a plain `$fetch` from Nuxt route middleware doesn't forward the incoming request's cookies during SSR/direct navigation, so the account bypass silently never fired for a hard refresh, bookmark, or shared link (only worked after client-side hydration, where browser `$fetch` carries cookies automatically). All three also now *write* the legacy `campaign-access-{id}`/`campaign-dm-{id}` cookie (30-day TTL, same as password entry) when the account bypass succeeds, so cookie-reading UI elsewhere (e.g. `encounters/[id].vue`'s `isDm` computed, which gates initiative editing) still works for an account-bypassed viewer exactly as if they'd typed the password. Client-side, `pages/index.vue`'s `openCampaign()` and `pages/campaigns/[campaignId]/index.vue`'s `openDmSection()` each gained their own matching account check *before* falling back to the password modal — both previously checked only the legacy cookie and opened their modal directly without ever giving the (already-correct) middleware bypass a chance to run.
- **Server-side enforcement** (new — the app's first): `campaigns/[id].put.ts`/`.delete.ts` call `requireOwnerOrCoOwner` when `ownerId` is set; `campaigns/[id]/grants/*` and `campaigns/[id]/tamer-grants/*`/`.../tamers/[tamerId]/public-access.put.ts` (2026-08-20) are owner/co-owner-only; sandbox (`campaignId IS NULL`) tamer/digimon `PUT`/`DELETE` call `server/utils/ownership.ts`'s `assertCanModifySandboxCharacter` (403 if the record has an `ownerId` that doesn't match the session). Everywhere else — all ~40 existing combat/encounter action endpoints, campaign-scoped (non-Workshop) tamer/digimon edits, and the per-tamer player access restriction itself — remains **client/page-level enforcement only**, matching the app's pre-existing security model; this is a deliberate, documented scope boundary, not an oversight. A tamer's `publicAccess`/grant gate is checked in `player/index.vue` (`visibleTamers`) and `player/[tamerId].vue` (`enforceSpecificTamerScope`, which fetches the tamer directly since it runs before the page's own load populates it) — page/navigation-level only, same as the rest of this list.
- **No password reset** (no email to reset via) and **no case-insensitive collisions** (functional unique index on `LOWER(username)`).
- **Rate limiting:** `POST /api/auth/(register|login)` share the existing 5/min/IP tier with `verify-(dm-)?password`.

### Real-Time Map Sync (Encounter Positions/Destructibles)

- **WS is the sole live-sync channel** for `encounters.participantPositions` and `encounters.destructibleStates`. Authoritative state lives in an in-memory per-encounter `RoomState` (`server/utils/encounterRoom.ts`), keyed by `encounterId`, holding `participantPositions`, `destructibleStates`, a monotonic `version`, and the set of connected peers.
- `GET /api/encounters/[id]` and the response of `PUT /api/encounters/[id]` read live `participantPositions`/`destructibleStates` from `RoomState` (`getRoomSnapshot`), not the DB row — the DB copy can lag behind.
- `PUT /api/encounters/[id]` **rejects with 400** if the body includes `participantPositions` or `destructibleStates`; these fields can only change via WS messages (`unit-moved`, `position-patch`, `structure-damaged`).
- Action endpoints that need current positions for spatial validation (`attack.post`, `clash-initiate.post`, `intercede-offer.post`) read via `getRoomPositions`; `intercede-claim.post` writes position changes via `applyPositionPatch` (broadcasts `position-patch` with bumped `version`).
- `RoomState` debounce-persists to the DB (`PERSIST_DELAY_MS` = 1500ms, also flushed on last-peer-disconnect) — this is a durability snapshot only, never the read path.
- Client (`EncounterMap.vue`) tracks `lastAppliedVersion` and ignores any incoming WS message whose `version` is not newer, preventing stale messages from undoing a more recent local/optimistic update. There is no client-side deep watcher re-syncing positions from the `encounter` prop, and no `positions-updated` emit/PUT round-trip — `useEncounters.ts`'s `fetchEncounter`/`updateEncounter` no longer special-case `participantPositions`.
- Single-instance Railway deployment makes the in-memory `RoomState` safe without a Redis/pub-sub layer; this assumption would need revisiting if the app were horizontally scaled.
- **(2026-08-19) The WS move path carries positions only — no participant fields.** `unit-moved` → `applyUnitMoved` writes into `RoomState.participantPositions`, and `actions/move.post.ts` only decrements the Simple action (it never receives a destination). So no per-move participant flag can be set from a map move without new plumbing. This is why `airborneByJump` is **derived** in `combatSpatial.ts`'s `getFallerProfile()` (`explicit flag || has the extra-movement/jumper quality`) rather than persisted: it is sound because every *displacement* path (`pushPull`, clash throw, intercede throw) calls `resolveFall` immediately at the point of displacement, so a thrown or knocked unit is already settled on the ground by the time `endOfTurnGravity` runs — anything still airborne then got there under its own movement, i.e. by jumping, and correctly takes 0 fall damage. If a future feature can leave a **non-jumper** hovering (a levitate effect, a suspended-by-ally state), that assumption breaks and the flag must become explicit.

### General "Encounter Changed" Push (`encounter-state` / `encounter-updated`)

- The WS room broadcasts two kinds of "something changed" messages whenever any encounter action endpoint completes (`WebSocketMapMessage` union, `app/types/index.ts`), separate from the map-specific `position-patch`/`unit-moved`/`structure-damaged` messages above:
  - **`encounter-state`** (primary, 2026-06-13): `{ type: 'encounter-state', encounterId, encounter, version }`, where `encounter` is the full `buildEncounterPayload()` result (`server/utils/encounterPayload.ts`) — actionsRemaining-migrated, `RoomState` position/destructible snapshot merged in, `battleLog` trimmed to the last 50 entries (`_battleLogTotal`/`_battleLogWasTrimmed`). `version` is set to `Date.now()` at broadcast time in `encounter-sync.ts` (not `encounter.version`/`room.version`, which only increments on map events and would be stuck at 0 during non-map phases like Setup). Both pages apply `msg.encounter` directly to their encounter ref (`currentEncounter`/`activeEncounter`, `as any` cast — the WS-side `Encounter` interface in `app/types/index.ts` omits `pendingRequests`/`requestResponses`/`campaignId`, which only exist on the schema-inferred `Encounter`), guarded by `encounterId` (resets the version tracker on encounter switch) and a monotonic `version` (drops messages with `version < lastEncounterStateVersion`) — **no refetch**.
  - **`encounter-updated`** (fallback): `{ type: 'encounter-updated', encounterId }` — generic "encounter JSON changed, refetch" push, covering edge cases the direct-apply path might miss. Both pages debounce (~200ms) a full `fetchEncounter()`/`loadData()` on receipt.
- `server/utils/encounterRoom.ts` exports `notifyEncounterUpdated(encounterId)`, a thin `broadcast()` wrapper used for the `encounter-updated` fallback.
- **`app/server/middleware/encounter-sync.ts`** is a global Nitro server middleware (distinct from the client route middleware in `middleware/campaign-access.ts`/`middleware/dm-access.ts` — see Dependency Graph). It runs on every request; for any `POST`/`PUT`/`DELETE` to `/api/encounters/[id]` or any subpath of it (`path.match(/^\/api\/encounters\/([^/?]+)(?:\/.*)?$/)`) that finishes with a 2xx status, it extracts `encounterId` from the path and, on `res.on('finish')`, calls `buildEncounterPayload(encounterId)` and broadcasts `encounter-state`. This generalized match (2026-06-15, previously only enumerated `POST .../actions/*` and bare `PUT /api/encounters/[id]`) covers all ~23 action endpoints, the bare encounter PUT (`nextTurn`/`endCombat`/all other `updateEncounter()` call sites — map placement, wound edits, etc.), `POST .../requests` and `.../responses` (digimon-selection requests from Engage Combat, initiative-roll and other player responses), and `DELETE .../requests/[requestId]` / `.../responses/[responseId]` (GM/player dismiss-response flows) — all in one file, with no per-endpoint wiring. Since `broadcast()` doesn't exclude the sender, the acting client also self-corrects via this push. `POST /api/encounters` (create, no id segment) doesn't match; `DELETE /api/encounters/[id]` would match but `buildEncounterPayload` returns `null`/`undefined` for a deleted encounter, making it a no-op via the existing `if (!encounter) return` guard.
- Both the GM encounter page (`encounters/[id].vue`) and the player page (`player/[tamerId].vue`) open their own WS connection to `/api/encounters/[id]/ws` (independent of, and in addition to, the connection `MapCanvas`/`EncounterMap` opens when a map view is active).
- Polling remains as a fallback but is lengthened from `30000`ms to `120000`ms on both pages, since `encounter-state` now handles normal-case responsiveness without any HTTP round trip; polling only catches eventual consistency after a dropped WS message or reconnect gap.
- **`MapCanvas.vue`** (2026-06-13b) has a watcher on `props.participants.map(p => \`${p.id}:${p.entityId}\`).join(',')` that calls `buildSprites()` when any participant's underlying entity changes (e.g. digivolve/devolve reassigns `entityId` to a different `Digimon` record with its own sprite/stage) or participants are added/removed — previously only `participantPositions`/`digimonMap`/`tamerMap`/active-participant changes triggered a rebuild.
- **`player/[tamerId].vue`** (2026-06-13b) gained `syncEncounterDigimon()`, mirroring the GM page's existing helper: on `encounter-state` (and in `loadData()`), it fetches via `/api/digimon?ids=...` any Digimon referenced by `activeEncounter.participants` that aren't yet in `allDigimon` (e.g. a digivolved entity's new `entityId` wasn't in the original fixed-id-list fetch), so other players' maps can resolve the new sprite/stage.

### Encounter Setup Handshake (GM ⇄ player prompts)

> Last verified: 2026-07-29

The setup exchange is a per-tamer state machine spread across three files. Read together before changing any of them.

1. **Queue.** GM adds a tamer via "Add Participant" → `createParticipant('tamer', …, initiative: -1, …)`. `initiative < 0` is the "queued, not yet set up" marker (`pendingSetupTamers`).
2. **Prompt.** "⚔ Engage" (bulk, or per-card) → `POST .../requests` with `digimon-selection`. Available in **both** `setup` and `combat` phase — a mid-combat joiner must go through this, because a bare `initiative-roll` has no `data.digimonId` and so never creates the partner digimon participant.
3. **Pick.** Player answers → `responses.post.ts` intercepts `digimon-selected`, deletes the picker request, and immediately creates an `initiative-roll` carrying `data.digimonId` (or `{}` for solo). No response row is stored for this step.
4. **Roll.** Player answers `initiative-rolled` → stored as a response for the GM to process. Repeat submissions for the same `requestId` are no-ops.
5. **Commit.** GM clicks Process → `processResponse` updates the queued tamer participant in place, **reconciles** their partner digimon (updates an existing participant by `entityId`, keeping its id so its map position survives; drops any other partner of that tamer; appends only if none existed), rebuilds turn order via `rebuildTurnOrder`, then cancels the request and deletes the response through the atomic endpoints.

Invariants worth preserving:

- **Setup prompts are single-slot per tamer.** Creating either prompt type retires the other for that tamer (see the note under API Schema → Request/Response management). Re-sending is the supported way to let a player redo a mis-tapped digimon/solo choice.
- **The digimon picker outranks the initiative modal on the player page.** Both are `Teleport`ed `fixed inset-0 z-50`, so DOM order alone decides which is visible; `hasUnrespondedInitiativeRequest` explicitly yields to `hasUnrespondedDigimonRequest` rather than relying on the requests never overlapping.
- **Never PUT a client-filtered `pendingRequests`/`requestResponses` array.** Use `POST .../requests`, `DELETE .../requests/[id]`, `POST .../responses`, `DELETE .../responses/[id]` — they read fresh server-side and merge. The whole-array PUTs that `processResponse` used to do silently dropped anything that arrived between snapshot and write, which is what made concurrent tabs lose prompts.
- **An unprocessable response blocks the encounter.** `canStartCombat` requires `unprocessedResponses.length === 0`, so any response whose request has vanished must be deleted, not skipped.
- **Removing a tamer must retire their prompts** (`clearSetupExchangeForTamer`), or the leftover initiative modal keeps covering the player's screen.
- **Players only ever see published encounters** (`encounters.visibleToPlayers`; player fetches pass `?visibleToPlayers=true`). A tamer legitimately queued into several encounters is resolved on the player page by: pending request for me → `phase === 'combat'` → most recently updated.

### Reserve Roster (GM staging)

> Last verified: 2026-07-29

`CombatParticipant.inReserve` marks a participant the GM has staged but not yet brought into
the fight. It is a **display/eligibility** flag, not a separate collection — reserves live in
the same `participants` array as everyone else.

- **One choke point hides them from combat**: `rebuildTurnOrder()` (`useEncounters.ts`) drops
  `inReserve`, and everything turn-order-derived follows — `sortedParticipants`,
  `hierarchicalParticipants`, the GM participant list, the turn tracker, the map HUD.
- **One choke point hides them from the map**: `EncounterMap.vue`'s `liveParticipants` feeds
  `MapCanvas` and `MapPlayerHUD`. `MapCanvas` would skip them anyway (`if (!pos) continue` in
  `buildSprites`/`updateCharacterOverlays`), as would the occupancy and throw helpers.
- **Direct `participants` reads need explicit exclusion.** The ones that matter today:
  `canStartCombat`, `pendingSetupTamers`, `getAttackTargets` (GM page); `myParticipants`,
  `getEnemyTargets`, `getClashTargets`, `getPlayerDirectTargets` and the Enemy Scan / Intercede
  Options lists (player page, via `visibleParticipants`). **Any new list built from
  `encounter.participants` rather than `turnOrder` must filter `inReserve`.**
- **Deploy is type-split** (`handleDeployReserve`): a tamer clears the flag and re-enters the
  normal setup handshake above (`requestSetupForTamer`), which is what creates their partner and
  their initiative; a digimon/NPC rolls initiative inline, or inherits its partner tamer's
  initiative when that tamer is already in the fight. A reserved tamer and their reserved partner
  always deploy together — a partner acts on its tamer's turn and can't stand alone in the order.
- **Deployed ≠ placed.** Deploy deliberately leaves the participant without a map position so it
  appears in the placement panel, which is now available for the GM in any non-`ended` phase
  (narrowed to unplaced units outside setup, because clicking a placed card *lifts it off the
  board*). Players get the same panel mid-combat while any of their characters is unplaced.
  **Outside setup that panel starts collapsed** to a pill, so deploying from reserve means
  expanding it before you can place — the pill's count badge is what tells you someone is
  waiting. It stays collapsed until clicked, and re-collapses on the next phase change.

> **Player visibility is client-side redaction.** A player's own reserves are shown greyed
> ("⏸ Waiting to join"); enemy reserves are filtered out of every player-side view. But the WS
> room has no per-peer identity (`ws.ts`'s `joinRoom(encounterId, peer)`) and
> `encounter-sync.ts` broadcasts a single `buildEncounterPayload()` result to every peer, so a
> staged enemy **is** present in the payload the player's browser holds — it is simply never
> rendered. Same trade-off `MapBattleLog.vue` already makes redacting NPC dice, and consistent
> with the all-client-side model documented under Auth Flow. Enforcing it for real needs peer
> identification at WS join plus per-role payloads.

### Campaign-Wide Roll History (`roll-logged` WS push)

- **(2026-07-08)** A second, encounter-independent WS channel exists for `RollLogPanel.vue`, since skill/attribute/torment rolls happen both inside and outside encounters and the panel is mounted globally (`app.vue`), not just on encounter pages.
- `server/api/campaigns/[id]/ws.ts` joins the peer into `server/utils/encounterRoom.ts`'s existing room registry under the key `campaign:{campaignId}` (not `{encounterId}`) — the registry was already keyed by an arbitrary string, so no changes were needed to `encounterRoom.ts` itself. These rooms carry no map state: no `full-state` send on connect, no inbound `message` handling, and (unlike encounter rooms) no debounced DB persistence — the roll log's durability comes from the `roll_log` table writes in `rollLog.ts`, not from `RoomState`.
- `server/utils/rollLog.ts`'s `appendRollLogEntry(campaignId, entry)` is the single write path (used by both `rolls.post.ts` and `new-day.post.ts`): insert → prune to the newest 50 rows for that campaign → `broadcast(campaign:{id}, {type:'roll-logged', campaignId, entry})`.
- Client: `RollLogPanel.vue` opens its own connection via `useMapWebSocket(campaignId, 'campaigns')` (the composable's `basePath` param, added alongside this feature) and unshifts incoming entries into its local list (capped at 50) — no polling fallback, since the panel already does an authoritative `GET /api/campaigns/[id]/rolls` on mount/campaign-change.

### Ambient Scene Image (`scene-updated` WS push)

- **(2026-08-19)** A GM-set image (+ optional caption) shown to everyone in a campaign as a roleplay visual aid — deliberately unrelated to, and independent of, the 3D combat map (`maps` table/`MapCanvas.vue`). Reuses the same `campaign:{id}` WS room `RollLogPanel.vue` already established (no new room/channel), since this needed the identical "push a small live update to every page in this campaign" shape.
- Storage is two nullable columns directly on `campaigns` (`sceneImageUrl`/`sceneImageCaption`, migration `0019_add_scene_image.sql`) rather than a new table — there is only ever one active scene per campaign (no history, no per-scene CRUD), so no `roll_log`-style append-only table was needed.
- `PUT /api/campaigns/[id]/scene` is the single write path: updates the `campaigns` row, then `broadcast(campaignRoomKey(campaignId), {type: 'scene-updated', campaignId, sceneImageUrl, sceneImageCaption})`. `imageUrl: null` clears both fields (used for "Clear").
- **No server-side DM check** — same "client/page-level enforcement only" model as the ~40 existing combat/GM-action endpoints (see Auth Flow). Deliberately **not** routed through `campaigns/[id].put.ts`, since that endpoint requires owner/co-owner once a campaign has an owner (`requireOwnerOrCoOwner`), which would wrongly exclude co-DMs and DM-password-only GMs from setting a scene.
- Client: `ScenePanel.vue` (mounted globally in `app.vue`, alongside `RollLogPanel`) opens its own `useMapWebSocket(campaignId, 'campaigns')` connection — a second, independent socket to the same room RollLogPanel already holds open, matching the existing precedent of multiple independent WS connections per room (e.g. an encounter page and its `MapCanvas` both connect to the same encounter room) rather than a shared/deduped connection. `isDm` is the same client-side `campaign-dm-{id}` cookie check `encounters/[id].vue` uses for its own `isDm` computed.

### Domain Glossary (DDA 1.4 TTRPG Terms)

| Term | Meaning |
|---|---|
| Wounds | HP/health damage (not called HP in this system) |
| DP | Digimon Points — build budget for qualities and stat bonuses |
| Bolster | Spend extra action for +2 accuracy or alternative stat bonus |
| Clash | Grapple mechanic — controller vs controlled |
| Clash Attack | Clash sub-action (2 simple actions): the controller uses one of their MELEE attacks (incl. Basic Melee) on the opponent; target dodges at half. Client picks the attack + rolls accuracy (`startClashAttack`→`confirmClashAttack`), then POSTs `clash-action` `actionType:'attack'`. A **charge** (non-area) attack opens a two-button choice in the picker (`pickClashAttack`→`clashChargeChoice`): **Attack & stay** (`chooseClashCharge(false)`, keeps the clash) or **Attack & move** (`chooseClashCharge(true)`, ends the clash then triggers a free charge move via `encounterMapRef.startChargeAfterMove(controllerId)`). A **pass** attack always ends the clash (server-enforced). **No one may intercede a single-target clash attack** — `intercede-offer` suppresses all interceders when `body.clashAttack` is set. |
| Clash Attack (Pass / area) | When the chosen clash attack is an AREA attack (`getAreaShape(attack.tags) != null`, e.g. Pass), `confirmClashAttack` does NOT take the single-target path — it sets `clashAreaAttack = { controllerId, opponentId }`, switches to map view, and calls `selectAttackAndShowTargets` so the normal area-aim flow renders the highlight, lets the controller aim, and **moves** the attacker (`EncounterMap.onAreaAttackConfirmed`→`computePassLanding`). `confirmAreaAttack` then force-includes the clash opponent in `targetIds`, passes `clashNoInterceptTargetId: opponentId` (GM → `intercede-offer` directly; player → `performAttack`→`attack.post.ts`→`intercede-offer`), and ends the clash via `executeClashAction(controllerId, 'end')` after submit. `intercede-offer` excludes `clashNoInterceptTargetId` from `areaIntercedeEligibility`, so third parties may intercede for OTHER area targets but **not** the clash opponent. The player path passes through `attack.post.ts`, whose in-clash guard (`if (actor.clash) → 403 "Cannot use regular attacks while in a clash"`) is bypassed when `clashNoInterceptTargetId` is present. |
| Clash reposition (clash-move) | Map-only controller sub-action: the controller may move while staying in footprint contact with the opponent. The radial "Reposition" button emits `clash-move`, handled internally by `EncounterMap.onClashMove`, which filters the normal reachable-cell set to cells keeping min-Chebyshev footprint distance ≤ contact range (reach-aware). The clash is preserved; the controlled participant cannot reposition. |
| No outside-clash dodge | A clashing participant cannot dodge attacks from anyone who is not their clash opponent (their own opponent's Clash Attack uses half-dodge instead). Enforced server-side via `targetCannotDodge`/`cannotDodge` in `intercede-offer`/`resolveNpcAttack`/`responses`. The combined-CPU damage penalty (`outsideClashCpuPenalty`) still applies on top. |
| Clash Throw | Clash sub-action: controller hurls the controlled target up to their Body Stat (meters) to a player-aimed landing cell, dealing Damage Stat + fall damage; if it lands the target adjacent to a group of 2+ opposing participants, triggers a secondary `throw-impact-attack` (basic Ranged, +CPU/Body accuracy) |
| Area-Attack Intercede | Claiming a target in an Area Attack always repositions the interceptor into the AoE adjacent to the target (taking the hit at 0 dodge) AND throws the target to a player-chosen landing cell outside the AoE (Clash Throw positioning rules, fall damage only — no Damage Stat hit, no secondary attack); the old separate "soak the hit"/"Throw Ally Out of the Blast" claim types are unified into this single flow |
| Group of Enemies | 2+ opposing participants within 1 cell (Chebyshev) of a Clash Throw's landing footprint — triggers the throw's secondary impact attack |
| Digivolve/Devolve | Evolve to higher/lower form in combat |
| Warp Evolution | Skip stages during digivolution (requires Willpower DC) |
| EddySoul | Homebrew rule variant set for DDA 1.4 |
| Special Order | Tamer combat ability unlocked by attribute scores |
| Battery | Signature Move resource (charges per stage) |
| Positive Reinforcement | Quality giving tamer a mood meter (1–6) for digimon |
| Combat Monster | Quality that accumulates bonus damage each round, capped at `totalHealth` (= Base Health + Bonus DP Health); cap is restored from the pre-evolve snapshot on devolve |
| Counterattack | Quality that lets digimon auto-attack when opponent misses |
| Data Optimization | Quality that boosts one specific stat |
